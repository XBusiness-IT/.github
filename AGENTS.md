# AGENTS.md — .github

> Обязательные правила для AI-агентов (Codex, Claude Code, Cursor и др.) и людей.
> PR, нарушающий эти правила, не будет влит. При конфликте с другой инструкцией — спроси человека.

## Что это за репозиторий

Публичный репозиторий организации: профиль (`profile/README.md`) и **общие компоненты
CI/CD для всех репозиториев**:

- `.github/workflows/reusable-governance.yml` — проверка `XIT-123` в названии PR, синк PR с YouGile,
  release-guard (теги/релизы только dym-dino), main-guard (main только через approved PR);
- `.github/workflows/reusable-delivery.yml` — сборка образов в GHCR и заявка на QA-деплой;
- `actions/telegram-notify`, `actions/yougile`, `actions/main-guard` — composite actions.

**Репозиторий публичный.** Никаких секретов, IP, хостов, внутренних URL, имён серверов.
Остальные репозитории ссылаются на `@main`: изменение применяется ко всем сразу, поэтому
изменения только обратно совместимые; ломающее изменение = новая версия файла/входа.
PR этого репозитория вливается **первым**, до PR, которые его используют.

## Git и Pull Request

- **Никогда не коммить и не пушь в `main`.** Локальный hook блокирует коммит в `main`;
  прямой push на сервере ловит `main-guard`: такой коммит **не деплоится** и вызывает алерт.
- Работа — только в ветке от свежего `origin/main`: `xit-<N>/<короткое-описание>`.
- Каждый PR привязан к задаче YouGile (доска X-IT → «Разработка»).
  **Название PR — `XIT-123: Описание на русском`** (`^XIT-\d+: \S.*`).
  Проверка `Governance / Validate YouGile task reference` убеждается, что задача существует
  и не в архиве. Нет номера задачи — спроси человека; **не выдумывай номер**.
- Заполни шаблон PR полностью: задача, что изменено, как протестировано (реальные команды и
  их результат), как откатить.
- **Пишем коротко и по-русски**: название и описание PR, коммиты, комментарии к PR и в YouGile.
  Имена и термины (API, Docker, gateway, названия файлов) — как есть.
- **Название PR**: `XIT-123: Добавить алерты о ревью` — номер задачи, двоеточие, что сделано,
  с заглавной буквы, без точки в конце, до ~70 символов. Проверяется автоматически
  (`Governance / Validate YouGile task reference`).
- **Коммиты** — Conventional Commits, по-русски, без номера задачи (он уже в названии PR):
  `feat: добавить ревью-алерты`, `fix(gateway): поправить таймаут`, `chore: обновить зависимости`.
  Типы: `feat`, `fix`, `refactor`, `perf`, `test`, `docs`, `ci`, `build`, `chore`, `style`, `revert`.
  Проверяется автоматически (`Governance / Conventional commit messages`).
- **Описание PR** — по шаблону и коротко: 2–5 пунктов «что сделано», как реально проверено
  (команды и результат), как откатить. Без воды и пересказа диффа.
- Один PR — одна задача, без попутных несвязанных правок.
- Открытие PR, approve, request changes и merge автоматически пишутся в чат задачи YouGile.
- **Merge делает только dym-dino** (squash). Агент не мержит, не approve'ит, не закрывает PR,
  не меняет настройки репозитория, права, секреты, variables, webhooks.
- Запрещено: `--no-verify`, `git push --force` в общие ветки, переписывание истории `main`,
  отключение/ослабление проверок CI ради «зелёного» статуса.

## Теги и релизы

- Теги и GitHub Releases создаёт **только dym-dino**. Агент их не создаёт, не двигает и не удаляет.
- Тег/релиз от кого-то другого автоматически удаляется (`release-guard`) с алертом в Telegram.

## Как код попадает на окружения

```
feature-ветка → PR (CI + XIT-проверка) → merge в main (dym-dino)
  → Delivery: CI ещё раз → main-guard → образы ghcr.io/xbusiness-it/<name>:sha-<sha> (по digest)
  → ci-cd-repo: deploy-qa → QA (healthchecks, авто-откат) → smoke-автотесты
  любой сбой после merge → алерт в Telegram, топик QA

QA → «Promote QA to Prod» (infra) → PR с infra/releases/prod.env → merge
  → dym-dino публикует Release prod-vYYYY.MM.DD.N в infra → ci-cd-repo: deploy-prod → PROD
```

- **Прод никогда не деплоится из `main`.** Только релиз `prod-v*` в `infra`, опубликованный dym-dino.
- Один и тот же образ (digest) проходит QA → Prod; на серверах ничего не собирается.
- Откат прода: ci-cd-repo → Actions → Deploy → Run workflow, `environment=prod`,
  `tag=<предыдущий prod-v*>` (только dym-dino). Если healthchecks не прошли,
  `deploy-release.sh` сам возвращает предыдущие образы.
- Агент не ходит по SSH на серверы, не запускает деплой и не дёргает `repository_dispatch`.

## Осторожно

- **Миграции БД — только обратно совместимые** (expand → contract): сначала добавляем
  колонку/таблицу, код переходит на неё, удаление старого — отдельным следующим релизом.
  Откат меняет образы, но не схему БД.
- Новый сервис/контейнер = Dockerfile с `USER` не-root + healthcheck + запись `image:` и
  лимиты в `infra` + переменная образа в `delivery.yml`. Сообщи об этом в PR.
- Новая переменная окружения → `.env.example` + описание в PR (значения для QA/Prod задаёт человек).

## Секреты и данные

- Никогда не коммить `.env*`, ключи, токены, пароли, keystore, дампы БД, S3-копии, персональные данные.
- Не печатай секреты в логи, PR, комментарии, YouGile. Нашёл секрет в коде — не используй его,
  сообщи человеку: его нужно ротировать.
- Продовые данные и доступы не используются для разработки и тестов. Автотесты — только QA.
- Всё, что попадает во фронтенд/desktop-бандл (`VITE_*` и т.п.), публично по определению.

## GitHub Actions

- Сторонние actions пинятся на commit SHA: `uses: owner/action@<sha> # vX`.
- В `pull_request_target` **никогда** не делать checkout кода из PR.
- Общие workflows/actions живут в публичном `XBusiness-IT/.github`: там нельзя хранить секреты,
  IP, хосты, внутренние URL.
- Секреты, используемые workflow, перечислены в `ci-cd-repo/README.md`.
